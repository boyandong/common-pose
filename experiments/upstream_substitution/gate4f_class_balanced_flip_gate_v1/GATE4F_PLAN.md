# Gate4F class-balanced DB9 customer Flip gate — prospective DEV derivative

This is a strict derivative of closed Gate4E, not its rescue. Its **only scientific change** is the customer's optimization requirement: Gate4E minimizes naturally usage-weighted Flip risk; Gate4F minimizes unweighted mean Flip risk over supported reference-output classes. `BALANCED_CUSTOMER_REQUIREMENT.md` freezes the same customer, Flip target and 30-accepted-block class-support rule already used for Gate4E's secondary balanced preservation. Gate4E artifacts remain unchanged. Same 19 DEV users and 654 files, same Gate4C paired outputs, Gate4D four-view TTA, upstream, canonical16 adapter, DB9 head, deployment features, candidate families, model hyperparameters, five subject-grouped outer folds, three fold-local calibration users, 5,000-block per-training-user cap, final 15-train/4-calibration allocation, coverages `[1,.9,.8,.7,.6,.5,.3]`, secondary diagnostics and prohibitions. The exact unchanged cohort and feature manifests are copied byte-for-byte from Gate4E. No VALIDATION or protected user is opened.

**Training objective change only.** Each training user contributes equal total weight. Within a user, every reference `y_GT` class occurring in that user's deterministic sampled training blocks contributes equal total weight, regardless of block count. Within that user/class, Flip and non-Flip each get half of its class weight if both occur; if only one occurs, that observed Flip state gets the whole class weight. Thus for user `u`, class `k`, Flip state `b`, every sampled block has weight `1/(N_user_classes × N_observed_flip_states_within_class × N_blocks_in_user_class_state)` before global normalization to total weight equal to the training-row count. No sampled class gets zero weight. GT reference class and Flip are used for **training weights/targets only**, never as deployment features. Non-learned method scores and Gaussian/analytic boundary implementations remain Gate4E's exact formulas; the Gaussian training error-distribution fit follows the same fold-local user-weighting formula as Gate4E, not the new classification loss weights.

**Primary evaluation/selection change only.** At every user and fixed coverage, rank by the same deployment score, accept `ceil(coverage × N)` with stable ties, then compute the frozen class-balanced Flip risk. Report balanced preservation, per-class risk/support, supported-class count, ordinary Flip risk/preservation, AUROC/AUPRC and the same Fisher/probability/physical secondaries. User is the unit: median/IQR/range and improved-user count, no pooled-frame inference. Select the method minimizing the **median across users of each user's trapezoidal class-balanced Flip-risk AUC on 30%–100% coverage**. Exact ties: lower median user balanced risk at 50%; then lower at 30%; then higher median across users of their worst supported-class preservation at 30% (the per-user minimum over classes with ≥30 accepted blocks); then simpler method by unchanged Gate4E simplicity order. No usage-risk, Fisher or class-picked method selection.

**Grouped empirical calibration for Requirement-B.** For each calibration user and nominal coverage, compute that user's score quantile separately within every full calibration `y_GT` class with ≥30 blocks; take the median of those class quantiles, then the median of the calibration-user values. Apply this threshold unchanged to each held-out user. This uses reference classes only on calibration users. Report nominal and achieved total held-out coverage, balanced and ordinary Flip risk, per-class support/risk, and user heterogeneity. It is user-grouped empirical calibration, not a formal finite-sample clustered-data guarantee. The final DEV 15/4 allocation is unchanged from Gate4E and uses the same threshold rule.

Freeze the selected family, final model, exact class-balanced weights, features, preprocessing, score orientation, calibration thresholds, code and SHA256. If balanced risk fails to improve or accepted class support collapses, report the negative result; do not retune, drop classes/users/DOFs, change consumer, rerun upstream/TTA, or open Gate4C VALIDATION or any protected/untouched confirmation users. Gate4E Requirement-U and Gate4F Requirement-B have different legitimate customers; do not declare a universal winner. Joint untouched system confirmation requires separate PI authorization.
