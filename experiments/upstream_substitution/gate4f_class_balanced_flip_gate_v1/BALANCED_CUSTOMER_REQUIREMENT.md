# Gate4F customer requirement — frozen before Gate4F comparisons

The customer is the same frozen DB9 trusted-8 Pose→Gesture LDA as Gate4E. For paired-valid blocks, `y_GT = C(x_GT)`, `y_API = C(x_PRED)`, and `Flip = 1[y_API != y_GT]`. Gate4E Requirement-U minimizes naturally usage-weighted Flip risk. Gate4F Requirement-B minimizes **class-balanced Flip risk**: for each held-out user and accepted subset, compute empirical Flip rate separately in each `y_GT` class with at least **30 accepted blocks**, then take the unweighted mean across those supported classes. Balanced preservation is one minus that mean. Classes below 30 are reported with their exact support and `null` risk; never imputed or silently treated as success. If no class is supported, that user/coverage is undefined and the method is ineligible for selection. All 19 users remain included. The supported-class count is reported at every coverage; a method cannot claim uniform class service by improving this mean while excluding difficult classes. No human semantic label is required.
